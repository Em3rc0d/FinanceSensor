# MK0 / 00 — Brainstorming

## Problem

Most personal-finance apps begin with a bank connection or require repeated manual categorization. FinanceSensor explores a different wedge: use digital evidence already generated by everyday financial activity, process it primarily on the phone, and reconstruct understandable financial state automatically.

## Core analogy

**AutoPulse for money / OBD-II for finances.**

A vehicle has multiple sensors and ECUs. A financial life has multiple evidence sources: email, banks, receipts, statements, wallets and future Open Finance connections.

The product should transform raw signals into:

- expenses;
- income;
- transfers;
- refunds;
- recurring charges;
- categories;
- merchant identity;
- anomalies;
- opportunities;
- simple explanations.

## User reality we must support

A customer may have simultaneously:

- several smartphones;
- Android and later iPhone;
- several email accounts;
- several banks;
- several bank accounts;
- several cards;
- several currencies;
- several financial identities;
- more than one financial tenant over time.

Therefore the phone cannot be the tenant.

## Experience hypothesis

The product should feel useful without requiring the user to become a finance expert.

Primary language:

```text
Entró dinero
Gastaste
Moviste dinero
Te devolvieron dinero
Se repite
Cambió
Hay algo por revisar
Encontramos una oportunidad
```

## Behavioral principle

Do not tell people they are “bad with money.” Show facts, context and options.

Instead of:

> Estás gastando demasiado en delivery.

Use:

> Delivery está S/75 por encima de tu nivel habitual. Si vuelves cerca de ese nivel, conservarías aproximadamente S/75 este mes.

## UX principle

**One viewport → one purpose.**

The Home and Sensor overview do not scroll vertically. Scroll is allowed only where sequence is intrinsic, such as movement history or evidence lists.

## Device hypothesis

Core value must run on ordinary modern smartphones. The architecture must not assume a flagship NPU or large on-device LLM.

Preferred processing ladder:

```text
metadata filter
   ↓
deterministic parser/rules
   ↓
lightweight classifier
   ↓
optional local ML/LLM fallback
   ↓
Needs Review if unresolved
```

## Cloud hypothesis

```text
Cloud Control Plane
        +
Edge Financial Data Plane
```

Cloud coordinates; device understands. Multi-device state can synchronize through E2EE envelopes.

## MK0 brainstorming output

The first product proof should answer:

1. Can we obtain the needed Gmail evidence in a production-compliant way?
2. Can ordinary Android devices process a bounded financial history locally with acceptable battery/RAM/time?
3. Can we correctly resolve overlapping evidence into canonical financial events?
4. Can two devices converge without exposing plaintext financial state to the sync server?
5. Can the result be understood in seconds through signature no-scroll surfaces?

Anything not needed to answer those questions stays outside MK0.
